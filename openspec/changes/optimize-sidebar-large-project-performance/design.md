## Context

参见 `proposal.md` 的 Why，以及 `specs/sidebar-performance/spec.md` 的行为要求。

当前目录 watcher 以 `ignoreInitial: false` 启动，chokidar 会为初始发现的每个文件触发 `add`。`add()` 对 Markdown 文件调用 `loadMarkdownFile()`，把正文一起放入 `mt::update-object-tree`；Renderer 的 `addFile()` 实际只保留元数据，因此正文在这个阶段是无效负载。项目树未初始化时，Renderer 把每条事件存入 `pendingTreeEvents`，`OPEN_PROJECT()` 再逐条调用树变更函数；每次变更都会在深层响应式数组上查找、插入和排序。

文件树由 `tree.vue`、`treeFolder.vue`、`treeFile.vue` 递归渲染。每个文件夹监听创建和重命名通知，每个文件监听重命名通知，并各自注册上下文菜单处理；节点数量增长时，组件、DOM、监听器和订阅同步增长。侧边栏拖拽则在每次 `mousemove` 时直接写入宽度响应式状态。

设计需要同时处理主进程初始发现、IPC 交付、Renderer 建树和渲染四个阶段，并保证扫描期间的真实变更、项目切换以及后续 watcher 事件不会丢失。

## Goals / Non-Goals

**Goals:**

- 把初始扫描的每文件正文读取和每节点 IPC 降为元数据快照或有界批次。
- 让初始树构建只触发有限次响应式提交，并保持节点、排序和后续事件一致。
- 让已挂载文件树行数与视口而非逻辑节点总数相关。
- 把节点级全局监听和上下文菜单处理集中到树容器。
- 把拖拽宽度更新合并到动画帧，并保持最终宽度和持久化语义。
- 为每一项优化保留可独立验证和回滚的边界。

**Non-Goals:**

- 不重新设计文件系统 watcher、文件格式、文件保存/恢复、编辑器或 Muya。
- 不改变侧边栏排序规则、选择规则、上下文菜单项、文件操作结果或错误提示。
- 不修改已提交的菜单栏拉平和侧边栏滚动修复。
- 不引入新的 Renderer 文件系统能力或改变 preload/contextBridge IPC 安全边界。
- 不承诺在没有测量基线的平台和文件系统上给出固定毫秒阈值；验收以相对基线、规模不增长和事件数量为准。

## Decisions

### 1. 初始扫描只发送元数据，内容按需加载

目录 watcher 的初始事件 SHALL 使用轻量元数据路径，包含 `pathname`、`name`、`birthTime`、`mtimeMs`、`isDirectory`、`isFile`、`isMarkdown` 等构建树所需字段，不调用 `loadMarkdownFile()`。打开文档继续走现有文件读取路径；文件 watcher 的外部变更继续读取正文并发送 `mt::update-file`。

选择该方案是因为 Renderer 的项目树只消费元数据，正文在初始阶段没有消费者。备选方案是延迟读取但仍逐节点发送带正文事件，或让 Renderer 丢弃正文；两者仍产生磁盘 I/O 和 IPC 序列化成本，不能解决根因。新建文件需要初始内容的特殊场景保留显式内容加载路径。

### 2. 初始发现使用快照加有界批次，并定义与增量事件的合并规则

在 watcher ready 前收集初始条目；ready 后发送一个快照，或按固定节点数发送少量批次。Renderer 在普通对象中构建树，完成排序后一次性赋值 `projectTree`。扫描期间发生的真实变更进入增量队列，在快照应用后按时间顺序重放，或与快照按键合并。

备选方案是保留逐事件发送但只在 Renderer 批处理；这能减少部分渲染次数，但仍产生大量 IPC 和主进程回调。另一个备选方案是完全依赖 ready 后重新读取目录；这会重复 I/O 并扩大竞态。快照加增量队列的复杂度更高，但可以同时控制 IPC 数量和变更一致性。

### 3. 树状态采用“逻辑树 + 扁平可见行”双表示

保留现有树节点作为展开、排序和文件操作的真相来源；Renderer 根据展开状态派生可见行数组，每行包含节点引用、深度、类型和是否展开。虚拟列表只渲染视口附近的行，并使用稳定的 `pathname` 或节点 id 作为 key。活动文件、键盘导航和程序化定位通过行索引滚动到目标行。

备选方案是只在递归组件上加 `content-visibility: auto`；它可能减少部分布局和绘制，但仍会创建所有组件实例、事件监听和响应式依赖，无法满足大目录的有界挂载要求。虚拟列表需要处理行高、输入框和菜单锚点，因此先以固定行高实现，再对创建/重命名输入行做局部例外。

### 4. 节点级通知和上下文菜单集中到树容器

`tree.vue` 或树容器注册一次创建/重命名/活动状态通知，使用活动路径或当前焦点把通知路由到目标逻辑节点；行组件只维护本地输入状态和必要的展示逻辑。上下文菜单在树容器上使用事件委托和 `event.target.closest()` 识别目标节点，避免每个节点注册长期 DOM 监听。

备选方案是继续在每个节点监听但用事件池或节流减少执行；这不能减少监听器数量，也无法避免大量节点被通知。集中路由需要在行复用和虚拟化后保证目标路径正确，因此目标路径必须来自逻辑节点而非 DOM 索引。

### 5. 拖拽宽度按动画帧合并，结束时提交最终值

拖拽期间把指针位置写入待处理值，使用 `requestAnimationFrame` 每帧最多更新一次 `sideBarViewWidth`；`mouseup` 时取消待处理帧、计算最终宽度并调用一次现有宽度持久化动作。最小宽度约束和现有持久化 API 保持不变。

备选方案是继续直接写入响应式状态或只在 `mouseup` 更新；前者放大大树布局压力，后者会让拖拽失去实时反馈。

### 6. 按阶段落地并保留回滚边界

实现顺序为：先加测量和回归测试；再拆分初始元数据与内容加载；再引入初始快照/批次；再做扁平可见行和虚拟列表；最后做事件集中与拖拽合并。每一步都应能独立验证和回滚，避免把 watcher、树模型和渲染一次性重写。

备选方案是一次性替换整个侧边栏数据层；风险过大，难以定位性能与行为回归，也不利于与正在进行的重构并行。

## Risks / Trade-offs

- [初始快照覆盖扫描期间的增量事件] → 在 ready 前后维护有界增量队列，定义按 pathname 的合并规则，并增加创建后立即删除、重命名和项目切换测试。
- [元数据路径遗漏打开文件所需字段] → 明确项目树元数据契约；打开文件仍走完整文件读取，增加编码、BOM、混合换行和错误语义回归测试。
- [批处理改变事件顺序] → 以路径和操作类型定义确定性顺序；对同一路径的 add/unlink/change 采用最后状态优先，并在测试中断言最终树和通知顺序。
- [虚拟列表破坏选中、焦点或输入框] → 用稳定 key 和逻辑行索引维护状态；对创建/重命名输入行固定挂载或显式滚入视口；增加折叠、跳转、右键和键盘导航测试。
- [集中事件路由在行复用时指向错误节点] → 路由只使用逻辑节点路径，不使用 DOM 行索引；在快速滚动和连续重命名场景下增加回归测试。
- [动画帧合并丢失最终宽度] → `mouseup` 强制提交最后指针位置并取消待处理帧；增加最小宽度和重新挂载持久化测试。
- [性能测试波动掩盖回归] → 同时记录操作次数、IPC 数量、读取次数和挂载行数等确定性指标，不只依赖墙钟时间；墙钟结果使用多次运行和相同构建比较。
- [与其它重构并行产生冲突] → 先以当前行为测试和干净工作区为基线，按文件边界拆小提交；不覆盖未提交的其它变更。

## Migration Plan

1. 建立或补充大型项目夹具与基线测量，记录初始打开时间、`loadMarkdownFile` 调用次数、初始 IPC 次数、树提交次数、挂载行数和拖拽帧更新次数。
2. 先实现元数据初始扫描与内容按需加载，保留旧内容事件路径用于文件 watcher；验证打开文件、编码和外部变更行为。
3. 引入初始快照或有界批次与增量合并；验证扫描期间变更、项目切换和后续 watcher 事件。
4. 将可见树改为扁平逻辑行加虚拟列表；验证滚动、展开/折叠、活动文件、输入框和上下文菜单。
5. 集中全局通知和上下文菜单，合并拖拽宽度更新；运行全量受影响测试和性能对比。
6. 每个阶段单独提交，便于比较收益和回滚；若出现行为回归，只回滚对应切片，保留测量与测试工具。
