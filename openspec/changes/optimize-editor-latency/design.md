## Context

参见 `proposal.md` 中 Why 部分。当前实现中，启动恢复会在发送初始状态前读取所有恢复文档，文档打开会执行全量解析并在主线程重建完整 block/DOM 树，tab 切换会重复上述完整流程并恢复整套历史栈。现有技术栈是 Electron、Vue 3、Pinia 和 TypeScript 版 Muya；本次设计必须在该栈内完成，不引入 Go、Python 或 Rust，也不替换 Muya 的状态、解析、渲染、序列化和历史模型。

性能收益必须按用户可感知阶段衡量，而不是只看总耗时：首窗可交互、活动文档可编辑、文档首屏可显示、tab 切换首帧和编辑响应。现有性能基线覆盖冷/暖启动、恢复 tab、多窗口、大文档和多 tab 场景，但缺少首窗与全部恢复、文件读取与编辑器可交互、tab 缓存命中等阶段的独立指标。

## Goals / Non-Goals

**Goals:**

- 让首窗和活动文档的可用时间不再随非活动恢复文档数量线性增长。
- 让打开文档时优先显示当前视口内容，并允许用户在非关键装饰完成前编辑。
- 让最近使用的 tab 切换复用已有解析或编辑状态，避免重复全量解析和完整树重建。
- 降低高频变更路径上的全量序列化、状态深拷贝、TOC、字数和哈希计算。
- 保持文件编码、BOM、换行、错误处理、选区、撤销、滚动、保存和恢复语义不变。
- 为三个阶段建立可重复、可比较的性能指标和回归门槛。

**Non-Goals:**

- 不重写 Markdown 解析器、Muya 状态模型、渲染模型或历史模型。
- 不引入 Rust、WASM、Python、Go 或新的原生运行时。
- 不在本次变更中实现完整 block 级虚拟化；该能力仅作为后续独立变更候选。
- 不改变 Electron renderer 沙箱边界或绕过 typed preload/IPC。
- 不改变用户可见的文档格式、编码探测结果、保存结果或恢复规则。
- 不以丢弃未保存内容、历史记录或正确性来换取启动或切换速度。

## Decisions

### 决策一：启动恢复采用“首窗可见、活动文档优先、其余后台恢复”的两层模型

将启动恢复拆为前置同步阶段和后台恢复阶段。前置阶段只负责创建首个窗口、恢复必要的 UI 状态、准备当前活动文档的轻量描述并使其尽快进入可交互状态；非活动文档正文在窗口可用后由受控后台任务恢复。

后台恢复任务需要有明确的任务身份和取消语义，确保窗口或 tab 在任务完成前关闭时不会写回过期状态。活动文档读取失败必须形成可理解的 tab 错误状态，不能阻塞首窗。

**考虑过的替代方案：**

- 保持当前全量恢复但改为并发读取：仍会让首窗依赖全部文档中最慢的一项，无法消除随 tab 数增长的问题。
- 仅把文件读取改异步：可改善主进程阻塞，但不能解决 renderer 仍等待全部文档状态的问题。
- 一次性重写启动器：影响面过大，且与本次纯架构优化目标不成比例。

### 决策二：恢复文档正文按需加载，tab 元数据立即可用

恢复时先建立 tab 的轻量元数据，包括标题、路径、顺序、是否活动、光标、滚动位置和未保存标记。正文只有在 tab 被激活、编辑器需要显示或后台预取策略允许时才加载。

对未保存文档必须优先保留内存中的内容，不能因为延迟正文加载而丢弃用户修改。外部文件变更、路径变更和恢复失败都要使轻量状态转入明确的失效或错误状态。

**考虑过的替代方案：**

- 所有 tab 都保持已加载正文：启动和内存代价仍随 tab 数增长。
- 只保留活动 tab：切换未缓存 tab 时仍需完整加载，但优于当前阻塞启动；可结合 LRU 使用。

### 决策三：文档打开采用“解析先于全量渲染、视口优先”的分阶段管线

保持现有 Markdown 解析输入和输出语义，但将可见性与完整性解耦。文档进入编辑器时先确保当前视口及其附近块可显示、可编辑，非视口内容、复杂装饰和统计信息在后台按需或空闲执行。

解析结果需要明确表示“状态已可用”和“渲染已完成”的区别，避免用户可编辑状态被错误地等同于完整渲染状态。跳转到未渲染区域时，必须先准备目标区域，并保持选区和滚动结果最终一致。

**考虑过的替代方案：**

- 全量解析后一次性渲染：实现最简单，但无法改善大文档首屏。
- 完全虚拟化所有 block：收益最大，但涉及选区、命中测试、拖拽和滚动高度，风险超过本次范围。
- 仅对代码块/公式延迟渲染：收益有限，因为 block 对象和 DOM 创建仍会阻塞。

### 决策四：tab 复用采用有界缓存与按需激活

对最近使用的 tab 保留可复用的解析状态或编辑状态，由 LRU 或等价策略限制数量或估算内存。缓存命中时只激活已有状态、恢复选区和滚动；缓存未命中时才执行完整打开流程。

缓存失效条件必须显式定义：磁盘内容变化、文件身份变化、编码变化、渲染状态不可恢复、内存压力或达到缓存上限。任何缓存释放都必须保留未保存内容、文档身份和重新加载所需信息，且不得丢失用户修改。

**考虑过的替代方案：**

- 为每个 tab 永久保留独立编辑器实例：切换最快，但内存随 tab 数线性增长，且后台编辑器生命周期复杂。
- 只缓存 Markdown 字符串：可以减少文件读取，但仍需重复解析和重建 DOM，收益有限。
- 不做缓存，只优化渲染：无法消除 tab 切换重复解析的问题。

### 决策五：历史记录与编辑器状态按需恢复，不做切换路径上的整套深拷贝

tab 切换优先恢复光标、选区、滚动和可见文档状态。历史栈保持文档隔离，并采用按需、增量或引用式准备方式，避免在首帧路径中深拷贝和序列化整个 undo/redo 栈。

需要明确“立即编辑”与“历史尚未完成非关键整理”并发时的正确性：输入必须被记录，切回后的撤销结果必须与原语义一致，不同文档之间不得污染历史。

**考虑过的替代方案：**

- 每次切换继续深拷贝完整历史：语义简单，但成本随编辑历史和文档大小增长。
- 完全不在内存保留历史：会导致撤销不可用或频繁落盘，不符合现有编辑体验。

### 决策六：高频变更路径改为按需、防抖或空闲计算

对于 Markdown 全文序列化、状态深拷贝、TOC、字数统计和 synthetic history 哈希等非即时必需工作，改为在需要时计算，或使用防抖、空闲调度和增量维护。需要区分“编辑正确性所必需”的数据和“界面派生数据”。

性能观测必须能报告每个阶段和关键后台工作的耗时，且不得把派生数据未完成误报为文档未打开。

**考虑过的替代方案：**

- 保留所有每次变更全量计算：实现最稳，但与多文档和长文档场景冲突。
- 仅靠用户不可见后台线程：renderer 主线程仍会被序列化、DOM 和状态操作占用。

### 决策七：先测量，再按阶段设门槛

扩展现有性能报告，统一采集：启动的首窗显示、活动文档请求、活动文档加载、编辑器可交互和全部恢复完成；打开文档的请求、读取、解析、首屏、可交互和后台完成；tab 切换的状态可用、首帧、可交互和缓存命中。

先建立优化前基线和可重复场景，再为每个阶段设定目标。优化必须按阶段独立验证，避免总耗时改善掩盖首屏或输入延迟恶化。

**考虑过的替代方案：**

- 只看端到端总耗时：容易掩盖关键路径后移。
- 只看 CPU profiling：无法直接反映用户感知和主线程输入延迟。

## Risks / Trade-offs

- [延迟加载改变恢复可见性] → 立即恢复 tab 元数据，仅延迟正文；对活动文档和未保存文档维持更高优先级。
- [后台恢复写回过期状态] → 为任务绑定文档身份和版本，关闭或变更时取消并丢弃过期结果。
- [视口优先渲染导致跳转时短暂空白] → 跳转前优先准备目标区域，并保证最终状态与完整渲染一致。
- [tab 缓存造成内存增长] → 使用 LRU 或等价上限，并在内存压力下释放缓存但保留未保存内容。
- [缓存失效遗漏导致显示旧内容] → 将文件身份、磁盘版本、编码和路径纳入缓存键或失效条件，并覆盖外部修改测试。
- [历史按需恢复造成撤销顺序错误] → 保持文档级历史隔离，先验证立即编辑与撤销场景，再逐步减少深拷贝。
- [延迟派生计算导致界面短暂不一致] → 明确哪些数据必须同步、哪些可异步，并提供最终收敛保证和测试。
- [分阶段优化掩盖其他阶段退化] → 每阶段独立埋点和独立门槛，禁止用后台完成时间替代首屏或输入延迟。
- [Muya 内部假设被破坏] → 不改变 Markdown、状态、渲染和历史的外部语义；先以最小接口扩展和测试锁定行为，再优化内部路径。

## Migration Plan

1. 扩展性能报告和基准场景，记录三类延迟的阶段指标并形成优化前基线。
2. 先实现启动恢复分层和活动文档优先，并验证多窗口、多 tab、关闭、失败隔离和未保存内容。
3. 再实现文档打开的分阶段可见性，验证编码、换行、跳转、选区和保存语义。
4. 再实现最近使用 tab 的有界复用和按需历史恢复，验证外部变更、缓存释放和撤销隔离。
5. 最后处理高频变更路径的全量计算和深拷贝，验证编辑、统计、目录和历史一致性。
6. 每个阶段均保留独立回滚点；若出现内容、历史或内存回归，可关闭对应缓存或恢复原有同步路径，而不影响已完成的观测能力。

## Open Questions

- 无必须在实现前回答的问题；缓存容量、后台并发度和每阶段性能门槛可在基线测量后按数据调整，不改变本设计的分层方式。
