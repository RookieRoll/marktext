## Why

当前应用的三个主要延迟痛点分别来自启动阶段等待全部恢复文档、打开文档时在主线程全量解析并重建渲染树，以及切换 tab 时重复执行完整的解析、DOM 重建和历史栈恢复。现有技术栈具备足够的优化空间，无需引入 Rust 或 Python，也无需重写 Muya 的核心状态、解析、渲染、序列化和历史模型。

## What Changes

- 将启动恢复拆成“首个窗口和活动文档优先可用”与“其余文档后台恢复”两层，首个可交互窗口不再等待全部恢复文档完成。
- 恢复期间只同步加载当前活动 tab 所需内容，其他 tab 先恢复元数据，并按需或低优先级加载正文。
- 为文档打开建立分阶段可观测性，分离文件读取、Markdown 解析、首批内容渲染和编辑器可交互等阶段。
- 在现有 Muya 渲染模型内优先完成当前视口所需内容的渲染，避免非关键内容阻塞首屏。
- 为最近使用的 tab 保留可复用的编辑器状态或解析结果，避免每次切换都重新解析 Markdown、重建完整 block/DOM 树。
- 将 tab 历史与编辑器状态的恢复改为按需、轻量或引用式处理，避免切换时深拷贝并恢复整个 undo/redo 栈。
- 缩减高频变更路径上的全量 Markdown 序列化、状态深拷贝、TOC 计算、字数统计和哈希计算，改为按需、防抖或空闲执行。
- 保持 Electron 安全边界、现有文件编码与换行语义，以及 Muya 的编辑、撤销、选区和滚动行为不变。

## Capabilities

### New Capabilities

- `startup-restore-performance`: 定义启动时首窗优先、活动文档优先加载、非活动 tab 后台恢复及其可观测性要求。
- `document-open-performance`: 定义文档打开的分阶段加载、视口优先渲染、非关键工作延后和打开耗时观测要求。
- `editor-tab-switch-performance`: 定义多文档 tab 切换时的状态复用、按需历史恢复、缓存边界和切换延迟观测要求。

### Modified Capabilities

- 无。

## Impact

- 桌面主进程：应用启动编排、状态恢复、窗口创建、文件读取与恢复任务调度。
- Renderer：编辑器 store、tab 激活流程、编辑器组件加载、状态恢复和性能埋点。
- Muya：状态获取与变更通知、block 树更新、inline 渲染、历史记录访问和相关缓存接口；不改变 Markdown、编辑、撤销和渲染语义。
- 性能工具与文档：扩展启动、文档打开和 tab 切换的分阶段指标、基准场景和回归验证说明。
- 不新增 Go、Python 或 Rust 运行时，不改变现有打包语言和 IPC 边界。
